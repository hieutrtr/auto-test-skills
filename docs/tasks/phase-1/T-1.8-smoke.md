## 4. TDD plan

This task is itself a *test* artifact (the smoke harness is the test), so the
RED → GREEN → COMMIT cadence collapses slightly. Concretely:

1. **RED** — write `smoke.sh` first, with assertion blocks that exit non-zero
   if any of: (a) the run dir is missing, (b) the trailing KEY=value block is
   missing, (c) `run.json.summary.total < 1` for pass-path, (d) no `failures[]`
   for fail-path. Run it once with the `auto-test` orchestrate already in
   place — expect green on bun (because the orchestrator was unit-tested in
   T-1.5). Confirm RED behaviour by deliberately seeding a malformed run dir
   under `/tmp` and re-running with `SMOKE_DEBUG_BREAK=1` (kept as a
   hand-toggle, not a permanent feature).

2. **GREEN** — fix any harness bugs, capture transcripts. The transcripts
   themselves are checked-in artefacts (under `skills/auto-test/tests/smoke/`)
   and the assertion *that they exist + parse correctly* is what gates the
   commit.

3. **REGRESSION** — re-run all four unit-test `run-all.sh` suites; expect 0
   regressions. Document tallies in `T-1.8-review.md`.

4. **COMMIT** — `test(phase-1): T-1.8 smoke test`.

### Why bun-fail (not just bun-pass)

INDEX §11 requires *3/3 smoke repos green or documented manual fallback*.
"Green" is unambiguous on the pass path but ambiguous on the fail path —
without a fail-path smoke we cannot prove the orchestrator (a) honors
PIPESTATUS, (b) propagates exit-code 1 through the dashboard, (c) records the
failure in `run.json.failures[]` and `summary.failed`. So we extend the
sandbox-runnable surface with `bun-fail` to cover the same code paths
(pipeline, parser, finalize, render) that jest/vitest would otherwise have
covered.

## 5. Cross-platform notes

- `smoke.sh` uses only the same toolchain established in T-1.1..T-1.7:
  `bash` 3.2, `mktemp -d` (POSIX), `cp -R` (POSIX, both BSD and GNU accept it),
  `python3` for JSON assertions, `grep -E`, `awk` POSIX patterns, `date -u +%s`
  (works on BSD + GNU). No `stat -c`, no `date -d`, no GNU `find -printf`,
  no `gzip --keep`, no `sed -i`.
- `command -v <bin>` for runtime probing — POSIX.
- Transcript wall-clock uses `python3 -c 'import time; print(int(time.time()*1000))'`
  for ms precision (matches the centralizer pattern).
- `set -uo pipefail` — `pipefail` is bash 3.0+; macOS `/bin/bash` 3.2 is the
  floor and supports it.

## 6. Manual fallback (jest + vitest)

When a contributor *does* have `node` and `npm`/`pnpm` installed, they can
verify the jest and vitest paths end-to-end with the following exact command
list. These commands are reproduced verbatim into
`docs/tasks/phase-1/PHASE-MANUAL-VERIFY.md` at iter 10 (Phase sign-off).

### Jest

```bash
cd /tmp
cp -R <repo>/skills/unit-test-runner/tests/fixtures/jest jest-smoke
cd jest-smoke
npm ci                                                  # installs jest@^29
bash <repo>/skills/auto-test/scripts/orchestrate.sh .   # runs auto-test
echo "exit=$?"                                          # expect 0 (1 passing case)
ls .test-runs/                                          # expect a single TS folder
cat .test-runs/*/run.json | python3 -m json.tool | head -40
```

Expected:

- exit 0
- `.test-runs/<ts>/run.log` non-empty
- `.test-runs/<ts>/run.json.summary.total >= 1`
- ASCII dashboard ends with `EXIT 0   all <N> tests passed`

### Vitest

```bash
cd /tmp
cp -R <repo>/skills/unit-test-runner/tests/fixtures/vitest vitest-smoke
cd vitest-smoke
pnpm install                                            # installs vitest@^1.6
# (or: npm i)
bash <repo>/skills/auto-test/scripts/orchestrate.sh .
echo "exit=$?"                                          # expect 0
cat .test-runs/*/run.json | python3 -m json.tool | head -40
```

Expected:

- exit 0
- ASCII dashboard prints `vitest (auto-detected)` row
- KEY=value trailing block parseable

### npm-flavoured Jest fail repro

To exercise the exit-1 path through jest specifically, edit `__tests__/sample.test.js`
in the copied fixture and force a failure (e.g. `expect(1).toBe(2)`), then
re-run `bash <repo>/skills/auto-test/scripts/orchestrate.sh .` — expect
exit 1, dashboard `✘ FAIL`, `summary.failed >= 1`. This step is documented
for thoroughness; it is *not* required by AC.

## 7. Risk register

| ID | Risk | Mitigation |
|---|---|---|
| R-1 | Smoke harness flakiness (timing-dependent assertions) | Assertions are *shape-based* (file presence, JSON structure) not time-based. The single timing measurement (`elapsed_ms`) is logged but not asserted against. |
| R-2 | Bun version drift between sandbox and contributor host changes parser output shape | Parser goldens already cover bun text format pinned by T-1.4. Smoke captures the *running* bun version in the transcript header for forensic value. |
| R-3 | Sandbox lacks `node`/`npm` → false signal that `auto-test` doesn't work for jest/vitest | Harness emits `[skip:<reason>]` with rc=0 and the manual fallback section §6 is the recovery path. AC-6 enforces. |
| R-4 | Transcripts grow committed-LOC over time | Transcripts are tiny (≈ 30 lines each); only one per real-runner-success path. Failure transcripts live in the run dir under `/tmp` and are *not* committed. |
| R-5 | Smoke harness side-effects pollute the repo | Harness operates exclusively under `mktemp -d` work-dirs; the only files written under the repo are the canonical transcripts under `skills/auto-test/tests/smoke/`. Verified by the harness running `git status -s skills/` before and after. |
| R-6 | `bun.lockb` (binary) in fixture causes permission / copy issues on some filesystems | Both `cp -R` and `cp -r` copy lockb opaque bytes intact; tested on macOS APFS. Linux ext4 path documented in §6 manual instructions. |
