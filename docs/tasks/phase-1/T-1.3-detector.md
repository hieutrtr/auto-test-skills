## 1. Title (from plan)

> `unit-test-runner/SKILL.md` + framework detector (`package.json` scripts,
> `vitest.config.ts`, `bun.lockb`).

Loop-step refinement (this iter): the detector lives at
`skills/unit-test-runner/scripts/detect.sh`. Given a `<project-root>` argument
it emits a single-line canonical JSON document on stdout describing the
detected framework, JS runtime / package manager, the canonical command to
run the tests, and a few diagnostic fields. Five fixture projects under
`skills/unit-test-runner/tests/fixtures/{jest,vitest,bun,mocha,playwright-runner}/`
exercise the detector. A 6th fixture (empty / no `package.json`) exercises the
`unknown` fallback. The JSON shape is the input contract for T-1.4 parsers
and T-1.5 orchestrator.

## 3. Acceptance Criteria

Carry-over from `IMPLEMENTATION-PLAN.md` row 1.3 + section §(e) heuristics:

| ID | AC | Measurable check |
|---|---|---|
| AC-1 | 5 fixture projects detect correctly | `tests/fixtures/{jest,vitest,bun,mocha,playwright-runner}/` each produces `framework` matching its folder name |
| AC-2 | Empty / non-JS project → `unknown` | Fixture without `package.json` → `framework == "unknown"`, exit code 0, JSON still well-formed |
| AC-3 | JS runtime detected from lockfile | `bun.lockb` → `runtime: bun, package_manager: bun`; `pnpm-lock.yaml` → `pnpm`; `yarn.lock` → `yarn`; default → `npm`. Validated on jest/vitest/bun fixtures (3 of the 4 PM variants) |
| AC-4 | `command` is a runnable string | `command` field non-empty when framework ≠ unknown; references the package manager (`bun run test`, `pnpm test`, `yarn test`, `npm test`) so the orchestrator can `eval` it |
| AC-5 | JSON shape stable | Output validates as JSON; keys: `schema_version`, `framework`, `runtime`, `package_manager`, `command`, `project_dir`, `test_script`, `markers`. `markers` is a sorted array of detected signals (e.g. `["jest.config.js","devDep:jest","script:test"]`) — used by T-1.5 dashboard for explainability |
| AC-6 | Cross-platform shell | No `jq` dep; uses `python3` for JSON parse with awk/sed fallback; no GNU-only flags (`stat -c`, `find -printf`, `readlink -f`) |
| AC-7 | Skill discoverable | `skills/unit-test-runner/SKILL.md` passes `validate-skill.sh` 8/8; description ≥ 40 chars, contains a trigger phrase + an anti-pattern; folder name == frontmatter `name` |
| AC-8 | Multi-framework first-match | Test fixture with both `jest.config.js` and `vitest.config.ts` resolves to **vitest** (priority order: vitest > jest > playwright-runner > mocha > bun, when both have config files) — documented in `references/framework-detection.md` and asserted by T1.3-12 |
| AC-9 | `project_dir` absolute | Detector resolves `pwd -P` of the input arg; symlink-stable |
| AC-10 | Exit codes | 0 = detected (incl. `unknown`), 2 = bad input arg (missing or non-dir). Never 1 (no IO failures expected for a read-only inspector) |

## 5. Risks + Mitigation

| # | Risk | Mitigation |
|---|---|---|
| R-1 | Heuristic ambiguity (project has both jest + vitest configs) | Documented priority order in `references/framework-detection.md`; T1.3-12 asserts the tie-break |
| R-2 | `package.json` malformed JSON crashes parser | `python3 -c json.load` wrapped in `try/except` → falls back to `framework: unknown` on parse error; documented as warning to stderr |
| R-3 | Lockfile heuristics miss yarn-classic-style projects without `yarn.lock` (e.g. workspaces root only) | Phase 1 fixture set establishes the contract for the common case; corner cases (workspaces, monorepos) deferred to Phase 3 multi-runtime task |
| R-4 | `bun.lockb` is a binary; `cat`-ing it must not be done | Detector only checks `[[ -f bun.lockb ]]` — never reads contents. Same for `bun.lock` (text variant introduced bun ≥ 1.1.30) |
| R-5 | Frontmatter description too short — Claude routing misses skill | Apply `skills-survey.md` §5 4-part template (≥ 600 chars, with explicit anti-pattern listing browser-test / integration-test / log tailing) |
| R-6 | `playwright-runner` fixture conflated with Phase 2 `browser-test` skill | SKILL.md §«When NOT to use» explicitly lists "playwright e2e in `tests/browser/` → use `browser-test` instead". The `playwright-runner` framework keyword refers only to the **`@playwright/test` runner used as a unit-test runner** (i.e. when there's no browser navigation in the test itself) |
| R-7 | Output JSON ordering nondeterministic across `python3` versions | Use `json.dumps(..., sort_keys=True)` |
