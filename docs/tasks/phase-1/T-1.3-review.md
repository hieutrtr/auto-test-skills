## 4. Findings

### F-1 — Bash 3.2 associative-array regression (fix-now)
First draft of `test-detect.sh` used `declare -A OUTPUTS=()` which is bash-4+
only. macOS dev box ships bash 3.2 by default, so the test bailed before
running any assertions. **Fixed by** caching outputs in named scalars
(`J/V/B/M/P/U`) plus a `get_doc()` case dispatcher. Documented as a future
gotcha in `T-1.3-review.md` §4.

### F-2 — `validate-skill.sh` chokes on path with `..` (fix-now)
Passing `tests/..` as the skill folder produced `basename ..` → `..`,
which then mismatched the frontmatter `name`. **Fixed by** canonicalizing
to `pwd -P` before invoking validate-skill.sh.

### F-3 — Marker token `script:test` is duplicated by language (defer)
A `package.json` with `scripts.test = "jest"` produces both `script:test`
and `script:test:contains:jest` markers. Mildly redundant but useful for
the dashboard ("the test script literally calls jest" vs "a test script
exists"). Keeping both — explainability over minimalism. No fix needed.

### F-4 — `playwright-runner` ambiguity vs `browser-test` (defer; documented)
A project with `playwright.config.ts` + `tests/browser/*.scenario.md` is
ambiguous: should T-1.5 orchestrator route it to `unit-test-runner` or to
`browser-test` (Phase 2)? The detector returns `playwright-runner` and
emits no opinion. **Mitigation**: `references/framework-detection.md` E-7
documents that the orchestrator (T-1.5) **prefers** `browser-test` when
`tests/browser/` is present. Phase-2 follow-up will make this routing
explicit.

### F-5 — awk fallback parser limited (defer to T-1.8)
`parse_pkg_python3` always wins on the dev box; the awk fallback path
handles only standard `"name": "value"` JSON formatting. If python3 is
absent and `package.json` is multi-line / has comments / uses single
quotes, the fallback may misclassify. Acceptable for Phase 1 (python3 is
~universal); T-1.8 smoke run on a python3-less container would be the
real test, deferred to that task.

### F-6 — bun framework heuristic conservative (defer to T-1.8 / Phase 4)
The `bun` framework branch fires only when (lockfile is bun) AND
(`package.json` exists). A bare `bun test` on a folder with **no**
`package.json` would currently return `unknown`. Real-world bun projects
always have `package.json` so this is academic, but documenting here in
case T-1.8 hits the corner.
