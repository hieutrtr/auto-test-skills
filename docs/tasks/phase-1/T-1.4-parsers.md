## 1. Title (from plan)

> Output parser cho 3 framework (jest TAP, vitest JSON, bun text) → canonical
> `TestRun` JSON.

### Loop-step refinement

The detector (T-1.3) emits a routing key. T-1.4 closes the runner half of the
skill: take the **stdout of an actual test run** in one of three input
formats (jest's `--json` reporter, vitest's `--reporter=json`, bun's plain
text), and emit a canonical `run.json` shape that downstream tooling
(`auto-test`, claude-bridge loop, future `flaky-detector`) can consume
without knowing which framework produced it.

### Why **`jest --json`** instead of "jest TAP"

The plan row 1.4 says "jest TAP" but Jest does not ship a built-in TAP
reporter — TAP comes via the community `jest-tap-reporter` package which
adds a runtime dep and a friction point to install. Jest's `--json` output
is **built-in, documented, and stable across the 28+ release line** (the
fields we read — `testResults[].assertionResults[].{title,status,duration,
failureMessages,ancestorTitles}` — have been present since Jest 22, ~2018).

This is a small, deliberate deviation from the plan wording, in line with
ARCHITECTURE §2 line 27: *"Run với JSON reporter nếu có (`--reporter=json`,
…)"* — i.e. the architecture itself prefers JSON reporters where available.
The plan's "TAP" phrasing pre-dates this clarification. Documented in
`references/parser-output-schema.md` so future-us doesn't relitigate.

Vitest also uses `--reporter=json` — the file shape is **almost identical**
to Jest's (Vitest documents this explicitly: "JSON reporter format follows
Jest's"). One parser implementation can therefore handle both with minor
keying differences; we still keep two scripts (`parse-jest.sh`,
`parse-vitest.sh`) so framework-specific quirks (vitest's `> ` separator
in `fullName`; jest's `ancestorTitles` array) stay isolated.

Bun has **no JSON reporter** as of bun 1.3 (Sept 2024 — see
[oven-sh/bun#11214](https://github.com/oven-sh/bun/issues/11214)) so we
parse its plain-text output. The format is stable and well-documented in
the bun source (`src/bun.js/test/`).

## 5. Risks + Mitigation

| # | Risk | Mitigation |
|---|---|---|
| R-1 | Jest / Vitest JSON shape drift between minor versions | Pin to documented stable subset (`testResults[].assertionResults[].{title,status,duration,failureMessages,ancestorTitles}`); golden test catches drift on next jest/vitest version bump |
| R-2 | Bun text format changes (new emoji, color codes, unicode) | Strip ANSI escapes before parsing; rely on stable line shapes `(pass)`, `(fail)`, `(skip)`, ` N pass`, `Ran N tests across …` — if these change, golden test fails noisy |
| R-3 | `failureMessages` containing newlines breaks naive line-based parsing | Use `python3` JSON parsing (handles escapes); never line-grep JSON |
| R-4 | ANSI color codes in bun stderr leak into parsed text | Pre-filter via `sed 's/\x1b\[[0-9;]*m//g'` (POSIX BRE compatible) before splitting |
| R-5 | Duration field absent on some cases (jest pending) | Treat missing `duration` as 0; document in schema |
| R-6 | Output JSON ordering nondeterministic across `python3` versions | `json.dumps(..., sort_keys=True, indent=2)` everywhere; trailing newline appended explicitly so `wc -l` is stable |
| R-7 | Vitest's `assertionResults[]` may have nested `> ` separators in `fullName` (vs jest's `ancestorTitles`) | Vitest parser splits on `' > '` (with spaces) to recover suite/case hierarchy; jest parser uses `ancestorTitles[]` directly |
| R-8 | "jest TAP" deviation in plan vs "--json" in implementation | Documented in §1 «Why» above + `references/parser-output-schema.md` + review file. ARCHITECTURE §2 line 27 already prefers JSON. |
| R-9 | Golden tests too brittle (whitespace / key-order diff fails) | All parsers emit `sort_keys=True, indent=2` + trailing newline; tests compare with `diff -q` (byte equality), but goldens are regenerable via the same script (no manual hand-rolling) |
| R-10 | Empty input / non-test exit (e.g. compilation error before any test ran) | All 3 parsers detect "no testResults / no fail-pass-skip lines" → emit empty `suites: []`, `summary` all zeros, `failures: []`; exit 0. Caller (T-1.5) reads `summary.total == 0` to decide whether to surface a "no tests ran" signal. |
