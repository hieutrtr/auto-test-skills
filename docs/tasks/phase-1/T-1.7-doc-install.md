## 4. TDD plan

RED → GREEN → REFACTOR per loop Rule 2.

1. **RED**: write `tools/tests/test-validate-skill.sh` first.
   - Positive cases: each of the 3 production skills must pass (`exit 0`).
   - Negative cases (one fixture per failure mode):
     - `fixtures/no-frontmatter/` — body but no leading `---`.
     - `fixtures/missing-name/` — frontmatter without `name:`.
     - `fixtures/missing-desc/` — frontmatter without `description:`.
     - `fixtures/name-mismatch/` — `name: foo` but folder named `name-mismatch`.
     - `fixtures/desc-too-short/` — `description: ok` (< 40 chars).
     - `fixtures/no-body/` — frontmatter but empty body.
   - Confirm linter exits non-zero on each negative.
   - Confirm `lint-all.sh` exits 0 across `skills/*`.
2. **GREEN**: port `spike/code/tests/validate-skill.sh` to `tools/validate-skill.sh`,
   add check 9 (anti-pattern keyword), add `lint-all.sh` wrapper.
3. **GREEN**: shrink top-level `README.md` install block to ≤ 5 lines.
4. **GREEN**: add `skills/README.md` mini-overview (≤ 25 lines, table of 3 skills).
5. **REFACTOR / VERIFY**: run lint → run all 3 skills' test suites → confirm zero regressions.
6. **DOCUMENT**: write `T-1.7-review.md` with self-review checklist.
7. **COMMIT**: `docs(phase-1): T-1.7 install + frontmatter lint` (loop Rule 4).

## 5. Risk register

| ID | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R-1 | Linter is too strict and fails on a future, legitimate SKILL.md (e.g. multi-line description in YAML block scalar) | Medium | Medium | Tolerate `description: >` and `description: \|` block scalars by extracting the *first* description line for the length check; add explicit fixture in Phase 4 if a multi-line desc lands |
| R-2 | "Anti-pattern" keyword check (AC-4) misfires if a future skill genuinely doesn't need anti-patterns | Low | Low | Make check 9 a **warning**, not a hard fail (lint exits 0 if only warnings) — soft enforcement with clear log line |
| R-3 | Cross-platform: BSD `awk` and GNU `awk` differ on `getline` semantics | Low | Medium | Linter only uses POSIX awk constructs (`/.../{...}`); avoid `getline`. Spike port already validated on macOS BSD awk |
| R-4 | README install snippet drifts from `ARCHITECTURE.md` §(g) plugin guidance | Low | Low | Reference §(g) verbatim in the snippet's intro line; AC-6 grep-asserts no premature `claude plugin install` mention |
| R-5 | Negative fixtures live under `tools/tests/fixtures/` and may be picked up by an over-broad `grep -r SKILL.md` from the user | Low | Low | Place each negative fixture under a leaf folder named `*-fixture` so the user sees they are intentional; document in `tools/tests/fixtures/README.md` |
| R-6 | `lint-all.sh` over-globs and recurses into `spike/code/skills/hello-test/` (Phase 0 prototype) | Low | Low | Hard-code `lint-all.sh` to walk only `skills/*`, **not** `spike/`; spike skill is exempt and validated by spike's own test |
| R-7 | A future contributor adds a 4th skill but forgets to run `tools/lint-all.sh` | Medium | Medium | Document the gate in `skills/README.md` ("contributor checklist: run `bash tools/lint-all.sh` before commit"); CI hookup deferred to Phase 4 |
