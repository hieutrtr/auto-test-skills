## Approach

Pure synthesis. No new measurements — each row cross-references an artifact already produced in T-0.1 → T-0.4. For each PRD metric:

1. Restate the target.
2. Name the measurement method (what `Phase 0` did, or what `Phase 1` *will* need to do).
3. Bind a status: ✅ **PASS** (measured, target met), 🟡 **PARTIAL** (structural side measured, behavioural side deferred), 🟦 **DEFER** (Phase 1 scope by design), 🔴 **BLOCKED** (cannot make progress without external dependency).
4. Cite the artifact (file + line / table / section).

Three deliberate non-goals for this memo:

- **No re-measurement** of T-0.4 numbers — those are signed off in `spike/T-0.4-review.md`.
- **No Phase 1 design** — Phase 1 carry-overs are listed but not specified.
- **No tech-pick ratification** — TS-vs-Bun, JSON-vs-JSONL, etc. land in `spike-memo.md`.

## 4. Phase 1 carry-overs (extracted from reviews 0.1–0.4)

These are deferred items, not blockers — sourced from each review's §Findings + §Issues/Pivot. They feed into Phase 1 backlog grooming.

1. **Re-measure per-syscall write `p99`** in Bun or Node with `performance.now()` once runtime is picked. Aggregate throughput is the strong signal; per-syscall is the formal claim. *(T-0.4 review §Findings #3, §Sign-off carry-over #1.)*
2. **Manual skill-activation eval** on a fresh Claude Code session: 5 prompts (P1–P5), with and without restart, recording which trigger `hello-test`. Result feeds G5 and the PRD "no restart" claim. *(T-0.2 review §Findings #2 + #4.)*
3. **`validate-skill.sh` as pre-commit hook / CI step.** Reusable infrastructure once Phase 1 ships 8 SKILL.md files. *(T-0.2 review §Findings #1.)*
4. **Description quality + anti-pattern enumeration** for real skills (`auto-test`, `unit-test-runner`, …). The fingerprint trick used by `hello-test` does not generalize to natural-language routing. *(T-0.2 review §Findings #3.)*
5. **Retention pass + `latest` re-point** on every finalize. Designed in T-0.3, not implemented in T-0.4. *(T-0.4 review §Sign-off carry-over #2.)*
6. **Redact rules from `config.json`.** Schema reserved in T-0.3 §3, not wired. *(T-0.4 review §Sign-off carry-over #3.)*
7. **Windows `LATEST.txt` fallback** if Phase 1 needs Windows support. *(T-0.4 review §Sign-off carry-over #4.)*
8. **Idempotence content-test** — same project + same commit → byte-equal `manifest.json` modulo timestamps. Phase 0 confirmed shape; content is a Phase 1 deliverable. *(This memo §2 row G6.)*
9. **Never `source` user-supplied config** — bash word-splitting bit T-0.4 once. Worth a short style-guide line. *(T-0.4 review §Issues row 1.)*
10. **Anthropic product question (out-of-band)**: is there a `/skills list` or equivalent introspection surface? If yes, G5 can move from manual to automated. *(T-0.2 review §Issues §"Risk register update".)*

## 6. Notes / open questions surfaced by writing this memo

- The PRD's G1 ("time-to-first-fail-detected < 30 s") is only meaningful once `auto-test` exists end-to-end. Phase 1 should aim to measure G1 as soon as the *first* runner+aggregator path lights up — not wait for full Phase 1 completion. Suggest staking a sub-milestone "G1-first-cut" inside Phase 1.
- The "shape" / "content" reproducibility split for G6 is implicit in PRD's "Idempotent shape" wording. Worth noting in Phase 1 acceptance criteria so we don't accidentally over-promise.
- G5 is structurally a "human-in-the-loop" metric for the foreseeable future. If Anthropic exposes `/skills list` or similar, G5 measurement gets cheap; otherwise Phase 1 should batch the manual run as a one-shot evaluation rather than a recurring check.
