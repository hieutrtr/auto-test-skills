- [x] **Failure mode documented?** Three classes of failure are documented:
  1. Sandbox limitation (this iter cannot probe Claude Code's discovery

     or false-positive on negative prompts) → mitigation: enrich description
     with more anti-pattern entries (xlsx-style); fallback: pivot to plugin
     packaging (`/plugins enable`) per T-0.5 / Phase 0 exit criterion.

## Findings (3-5 bullets cho memo cuối Phase 0)

1. **Validator is reusable infrastructure**, not throwaway. Phase 1 will
   produce 8 SKILL.md files (`auto-test`, `unit-test-runner`,
   `test-log-centralizer`, etc.); the same `validate-skill.sh` should be
   bolted into a pre-commit hook or CI step to prevent malformed frontmatter
   shipping. Current set of 8 checks is conservative (folder-name = name,
   length ≥ 40); Phase 1 may want to extend with `allowed-tools` field
   parsing and a "description includes ≥ 1 trigger keyword and ≥ 1
   anti-pattern keyword" rule.
2. **Sandbox introspection gap is real and load-bearing.** No tool in the
   Claude Code agent surface (Bash, MCP, or otherwise) lets us ask "which
   skills did you discover?" or "trigger discovery now". This means G5
   (skill activation correctness) must always be validated through a
   human-in-the-loop manual procedure — at least until Anthropic exposes a
   `/skills list` or equivalent. Phase 1 install doc must include that
   procedure (4 steps, < 5 minutes). Note for T-0.5 memo.
3. **Trigger fingerprint pattern works for spike, not for prod.** Using a
   pseudo-unique phrase (`hello-test ping`) makes activation attribution
   trivial in a small manual test, but real skills (`auto-test`, etc.)
   need natural-language description routing on phrases that overlap with
   normal English ("test", "verify", "kiểm tra"). Phase 1 needs to invest in
   description quality + anti-pattern enumeration (xlsx pattern) to keep
   false-positive rate manageable. Anti-pattern density may be the single
   most important variable for G5 — flag for ad-hoc A/B in Phase 1 if budget
   permits.
4. **Restart-required question still open.** PRD §"Plugin Packaging" claims
   "không cần restart Claude Code session" after drop-folder install. The
   manual-verify procedure in T-0.2-hello-test.md is structured to test
   this empirically (run sequence twice, with/without restart). Result
   should land in T-0.5 memo and propagate to Phase 4 install doc.
5. **`allowed-tools` confirmed canonical (provisionally).** T-0.1 already
   surfaced this; the hello-test prototype sticks to `allowed-tools: Bash`
   without observable issue at the structural level (frontmatter parses).
   Behavioural confirmation (Claude actually honours the restriction) is
   another item for the manual run — fingerprint output uses only `Bash`,
   so this is testable.
