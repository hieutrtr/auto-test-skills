## 1. File-Format Decisions (per artifact)

ARCHITECTURE §(b) names five artifact types in a run folder. Each gets one
explicit format:

| Artifact | Format | Rationale |
|---|---|---|
| `run.log` | **Plain text** (UTF-8, append-only) | `tail -f`, `grep`, `Read` work without a parser. Subprocess `>>` and shell tee both Just Work. ARCHITECTURE §(b) explicitly types it as "raw stdout + stderr append-only". |
| `manifest.json` | **Single JSON** (one root object), atomic write via `tmp + rename` | Index file. Read-once by agents (G2). Updates after `run.log` is finalized — never mid-run, so contention is zero. |
| `run.json` | **Single JSON** (TestRun with nested suites/cases) | Per ARCHITECTURE §(f), v1 is "all in file". Written once at end of run by `finalize-run.sh`. Agents `jq` query for specific cases. |
| `events.ndjson` *(optional, v1.1)* | **NDJSON / JSONL** (one JSON object per line) | If we ever need a structured time-ordered event stream (skill orchestration timeline, retries, etc.), NDJSON is the right primitive — append-friendly, line-oriented grep works. **Defer to v1.1**: not required by ARCHITECTURE §(b)'s file list, would add a write path before we know we need it. |
| `browser-console.log` | **Plain text** (one line per console message, prefixed with level + timestamp) | Same reasoning as `run.log`. |
| `screenshots/*.png` | **Binary PNG** (Playwright default) | Indexed via path in `manifest.json.artifacts`. |
| `flaky-report.json` / `coverage-summary.md` | Single JSON / Markdown | Final-form artifacts produced by their respective skills; cited by manifest. |

### Why **not** wrap `run.log` in JSON / NDJSON?

Tempting to make every line a `{ts, source, level, message}` JSON object so
agents can `jq` filter. Three reasons we don't:

1. **Subprocess output is byte-stream, not line-stream.** Test runners emit
   ANSI escapes, multi-line stack traces, partial lines, progress bars. Forcing
   each fragment into JSON requires an in-band parser per byte — fragile and
   defeats the "raw" property ARCHITECTURE §(b) explicitly chose.
2. **Agent doesn't need it.** The structured queries (which test failed, which
   file, what error) are answered by `run.json` (TestSuite/TestCase). `run.log`
   is for the long-tail "show me the full stderr trace" case where any
   structuring is overhead.
3. **G2 pressure point is `manifest.json` + `run.json`, not `run.log`.** The
   < 5s budget for "find what failed" is met by reading the index files; the
   log is only consulted as a deep dive.

If we ever need structured event entries (e.g. for `flaky-detector` retry
sequencing), they go in `events.ndjson`, side-by-side with `run.log`.

## 2. Directory Layout

Locked exactly as ARCHITECTURE §(b):

```
<project>/.test-runs/
├── 20260505T142318Z/                <- UTC ISO-8601 compact, sortable
│   ├── manifest.json
│   ├── run.log                      <- aggregated (or symlinked from per-source)
│   ├── run.json
│   ├── browser-console.log          (only if browser-test ran)
│   ├── events.ndjson                (only if needed in v1.1; absent in v1)
│   ├── screenshots/
│   │   ├── homepage.png
│   │   └── checkout-fail.png
│   ├── flaky-report.json            (only if flaky-detector ran)
│   ├── coverage-summary.md          (only if coverage-reporter ran)
│   └── manual-checklist.md          (only if manual-test-helper ran)
├── 20260505T133012Z/
├── latest -> 20260505T142318Z       <- symlink, atomic re-point
└── config.json                      <- retention overrides, redact rules
```

### Decisions

- **Run-id format**: `YYYYMMDDTHHmmssZ` — UTC, sortable lexicographically,
  filesystem-safe (no `:`), short. Reject `RFC3339` (`2026-05-05T14:23:18Z`)
  because of the `:`.
- **Symlink for `latest`**: matches ARCHITECTURE example. Update via
  `ln -sfn 20260505T142318Z latest` (force, no-deref) — atomic on POSIX.
  Windows fallback: text file `LATEST.txt` containing the run-id (skill helper
  reads either; documented in T-0.4).
- **Multi-framework subfolder** (per ARCHITECTURE §(e)):
  `<run-id>/backend/run.log`, `<run-id>/frontend/run.log`,
  top-level `<run-id>/manifest.json` aggregates both. Same shape, one more
  level of nesting; supported in v1.
- **Worktree-friendly** (per PRD §6): `.test-runs/` is project-relative, so
  worktrees auto-isolate. `.gitignore` ships with `.test-runs/` entry to keep
  the directory un-tracked.

## 3. Schema Definition

Lock the **minimum stable contract** that consumers (claude-bridge loop,
agents reading `Read`, future SQLite v2) can rely on. Per ARCHITECTURE §(d)
the loop only reads four fields — those are the **load-bearing** keys; the
rest are advisory.

### `manifest.json` (top-level, written once at run finalize)

```jsonc
{
  "schema_version": "1",                      // bump on breaking change
  "run_id": "20260505T142318Z",               // matches folder name
  "project": "/Users/foo/code/bridge-bot",    // absolute path
  "started_at": "2026-05-05T14:23:18Z",       // ISO-8601 with colons (display)
  "finished_at": "2026-05-05T14:23:32Z",
  "duration_ms": 14217,
  "framework": "bun:test",                    // primary; multi → "multi"
  "runtime": "bun-1.1.4",                     // tool + version
  "command": "bun test",                      // exact shell invoked
  "exit_code": 1,                             // 0=pass, 1=fail, 2=undetected
  "summary": {                                // load-bearing for loop §(d)
    "total": 42,
    "passed": 39,
    "failed": 3,
    "skipped": 0
  },
  "failed_cases": [                           // load-bearing for loop §(d)
    {
      "name": "Login > rejects bad password",
      "file": "tests/auth.test.ts:42",
      "error": "expected 401 got 500"
    }
  ],
  "log_path": ".test-runs/20260505T142318Z/run.log",   // load-bearing
  "artifacts": {                              // pointers, all relative
    "log": "run.log",
    "json": "run.json",
    "browser_console": null,
    "screenshots": [],
    "flaky_report": null,
    "coverage_summary": null,
    "manual_checklist": null,
    "events": null
  },
  "layers": ["unit"],                         // which layers ran
  "timeouts": [],                             // workers killed by timeout
  "redactions_applied": ["AUTH_BEARER", "API_KEY"]  // for auditability
}
```

### `run.json` (structured TestRun per ARCHITECTURE §(f))

```jsonc
{
  "schema_version": "1",
  "run_id": "20260505T142318Z",
  "suites": [
    {
      "id": "tests/auth.test.ts",
      "name": "Auth",
      "file": "tests/auth.test.ts",
      "duration_ms": 312,
      "status": "failed",
      "cases": [
        {
          "id": "tests/auth.test.ts::Login::rejects_bad_password",
          "name": "Login > rejects bad password",
          "status": "failed",                 // passed|failed|skipped|flaky
          "duration_ms": 12,
          "error_msg": "expected 401 got 500",
          "error_stack": "...",
          "retry_count": 0
        }
      ]
    }
  ]
}
```

### Field-shape rules

- All timestamps are ISO-8601 UTC with `Z` suffix.
- All durations are integer milliseconds.
- All paths in `manifest.json.artifacts` are **run-folder-relative**
  (so the manifest is portable / archivable).
- All paths in `manifest.json.failed_cases[].file` use `path:line` for
  click-through (G2). Line is required when known, omitted (no `:`) otherwise.
- `error_stack` is opaque text — agents read it as a blob.

### What's **not** in v1

- LogEntry table (`{run_id, ts, source, level, message}`) — would only matter
  if we adopt `events.ndjson`. v1 keeps `run.log` plain.
- Per-suite hierarchy beyond depth 2 (suite → case). Nested describe blocks
  flattened by the parser into a single `name` ("Auth > Login > rejects ...").
- Cross-run history index (SQLite). Defers to ARCHITECTURE §(f) v2.

## 4. Concurrent-Write Strategy

INDEX.md open-Q3. Three real concurrency vectors to defend against:

1. **Within one run**: ARCHITECTURE §1 spawns `unit-test-runner` and
   `integration-test-runner` via `Promise.all`. Both append to the same
   `run.log` simultaneously.
2. **Across runs**: a user / claude-bridge worktree triggers `auto-test`
   while another instance is finishing — risk of touching `latest` symlink
   simultaneously.
3. **Across processes within one runner**: parallel test workers in modern
   runners (Vitest, pytest-xdist) emit interleaved stdout to the runner's
   parent, which then forwards to `run.log`. Already serialized by the
   runner — not our concern.

### Strategy: per-source files + post-finalize merge (chosen)

- Each layer writes to its **own** stream file:
  `<run-id>/streams/unit.log`, `streams/integration.log`,
  `streams/browser.log`, `streams/skill-orchestrator.log`.
- `streams/*.log` are written via `>>` (append) from subprocess `tee` —
  no inter-stream contention because each file has one writer.
- At end of run, `finalize-run.sh` concatenates the per-source streams in
  fixed order (`unit → integration → browser → orchestrator`) into the
  top-level `run.log`. (`cat` is fine; no interleaving because all writers
  closed.)
- Alternative: top-level `run.log` is a **symlink** to a single canonical
  stream when only one layer ran. Saves one copy. Pick at finalize time
  based on `manifest.layers.length`.

### Why not `O_APPEND` + single shared file?

- POSIX guarantees atomic append for writes ≤ `PIPE_BUF` (typically 4096 bytes
  on Linux, 512 on macOS). Test-runner output frequently exceeds 4096 bytes per
  write (multi-line stack traces). Interleaving is observable in practice.
- Cross-platform: NTFS (Windows) does not give the same guarantee; a v1 that
  works fine on macOS/Linux but corrupts on Windows is a future support tax.
- Wraps the issue in a per-process `flock(2)`? Works, but every append pays
  syscall + contention. p99 < 50ms target gets harder as concurrency rises.

### Why not per-PID subfolder?

Considered. Would give us strict isolation, but: (a) merging back into a
single `run.log` for the user is more code, (b) PID isn't stable across
process restarts mid-run, (c) layer-per-file is simpler to reason about
because layers are the unit of orchestration anyway. Per-source > per-PID.

### Cross-run safety (latest symlink)

- Symlink update via `ln -sfn` is atomic on POSIX (rename(2) semantics).
  Two parallel writers race; loser's symlink wins, manifest is still durable.
  Acceptable: the loser's run is still discoverable by run-id, just not via
  `latest`. Document: "for true parallel runs, address by run-id, not
  `latest`."
- For multi-agent claude-bridge use (Risk register R4): per-worktree
  `.test-runs/` is a hard isolation boundary. Symlink contention only happens
  inside one worktree, where one auto-test invocation at a time is the
  norm.

### `manifest.json` updates

- Written once at finalize via `tmp + rename`. Atomic on POSIX. Never
  partially-written state observable.
- If long-running tests want **periodic** progress in `manifest.json`
  (e.g. heartbeat for a 10-min browser run), use the same tmp+rename
  pattern, polled at a coarse cadence (≥ 1s). Defer to a v1.1 feature
  request — v1 finalize-only is sufficient for MVP.

### Concurrency benchmark target (T-0.4 carries this)

- 100 concurrent appends from subprocess workers → file uncorrupt
  (lines well-formed, no interleaving), p99 < 50ms (Phase 0 row 0.4 AC).
- T-0.4 will exercise both the per-source path (expected to comfortably pass)
  and the rejected `O_APPEND` baseline (sanity-check the rejection).

## 5. Retrieval Pattern (G2 ≤ 5s)

PRD G2: agent `Read` < 5s, no multi-file grep. Three optimizations:

1. **`latest` symlink**. Agents address `<project>/.test-runs/latest/...`
   without knowing the run-id. One `Read` to canonical path, no `ls + sort`.
2. **`manifest.json` is the entry point**. ≤ 4KB typical, parses in microseconds,
   contains `summary`, `failed_cases`, `log_path`, all artifact pointers.
   Single `Read` answers "did the run pass?" and "where do I look for
   detail?". This is the load-bearing read for G2 and the loop §(d) contract.
3. **Failed-case `file:line` references**. Each failure entry contains a
   `path:line` triple agents can `Read` (Claude Code's `Read` accepts
   `offset` + `limit`) — they jump straight to the failing assertion in
   source, no `grep` over `run.log`.

### Worked example (5-second budget)

```
1. Read .test-runs/latest/manifest.json                  # ~3ms IO
2. exit_code = 1; failed_cases = [...]                   # ~1ms parse
3. For each failed_case (typically 1-5):
     Read failed_case.file at line ±10                   # ~3ms each
4. (only if needed) Read .test-runs/latest/run.log       # ~50-200ms for 10MB
```

Total: 50-300ms for typical small-medium project. Well under 5s with
margin for IO weather. **No grep over `run.log` in the happy path.**

### Anti-patterns banned by this design

- Asking agent to `ls .test-runs/` and sort. → Use `latest` symlink.
- Asking agent to `grep` over multiple log files. → Use `manifest` entry
  point + `failed_cases[].file:line`.
- Splitting state across multiple JSONs. → `manifest.json` is the index;
  detail lives in `run.json` (one read away, only when needed).

## 6. Rotation / Retention

ARCHITECTURE §(b) policy is locked; this section makes it operational.

### Tiers

| Tier | Age / count | Action | Disk impact |
|---|---|---|---|
| Hot | last 10 runs | keep full | full |
| Warm | runs 11–30 (or > 7 days, whichever first) | gzip `run.log` → `run.log.gz`, drop `screenshots/` | ~10× shrink |
| Cold | > 30 days | delete entire run folder | 0 |

`run.json` and `manifest.json` are **never** dropped during warm tier — they
are the queryable index for trend analysis and stay tiny (~KB each).

### Trigger

- **Lazy**: at the start of every `auto-test` invocation, before creating the
  new run folder. Cost: one `readdir` + a few `mtime` checks. Adds < 50ms
  to a fresh run start.
- **No daemon**, no cron. Aligns with PRD's "no daemon, no server" stance.

### Configurability

`<project>/.test-runs/config.json`:

```jsonc
{
  "retention": {
    "keep_full": 10,
    "warm_after_count": 10,
    "warm_after_days": 7,
    "delete_after_days": 30
  },
  "redact_rules_path": ".test-runs/.redact-rules"
}
```

User override only; defaults work for the indie-dev persona.

### Edge cases handled

- **Worktree-aware**: `.test-runs/` is per-worktree, so retention is local —
  no cross-worktree GC required.
- **Manual delete by user**: skill must not assume run folders are present
  in monotonic order. `auto-test --cleanup` (Phase 4) walks `readdir`
  directly, not by index.
- **Symlink stale**: `latest` may point to a deleted run after retention
  GC. Cleanup re-points to the newest surviving run; if none, deletes
  `latest`.

## 7. Decisions Summary (one-page reference)

| Topic | Decision | Rejected |
|---|---|---|
| `run.log` format | Plain text, append-only | NDJSON, single JSON |
| `manifest.json` format | Single JSON, written once at finalize, atomic via tmp+rename | Append NDJSON, periodic rewrite |
| `run.json` format | Single JSON, written once at finalize | NDJSON, SQLite |
| `events.ndjson` | Defer to v1.1 (only if needed) | Required v1 artifact |
| Run-id format | `YYYYMMDDTHHmmssZ` (UTC, no `:`) | RFC3339 with colons |
| `latest` pointer | POSIX symlink (force-no-deref re-point); Windows: `LATEST.txt` | File copy, hard link |
| Schema versioning | `schema_version: "1"` field on each JSON artifact | Folder-name-versioned, no version field |
| Concurrent stream writes | Per-source stream files + post-finalize merge | Single shared `run.log` with `O_APPEND`, per-PID subfolders |
| Manifest write | tmp + rename (atomic) | In-place edit, append journal |
| Retrieval entry | `latest/manifest.json` (one Read, ~4KB) | `ls + sort`, multi-file grep |
| Retention trigger | Lazy at run start | Daemon, cron, on-write |
| Redact rules | Default minimal list + project override file | Hard-coded, none |

## 8. Open Questions Carried Forward

For T-0.4 (prototype):

1. **Stream-merge tool**: shell `cat` vs Bun fs.append vs Node `pipeline`.
   Decision in T-0.4 by ergonomics + portability.
2. **Windows symlink permission**: developer account vs admin elevation. T-0.4
   prototype documents the fallback path (`LATEST.txt`) as the supported
   Windows route.
3. **Redact regex perf**: PRD §6 wants secrets scrubbed before bytes hit
   disk. Inline scrub via `tee` filter vs post-write rewrite. T-0.4 picks
   inline (post-write means secrets briefly hit disk → rejected for v1).

For T-0.5 (decision memo):

4. **Bun vs Node helper-script runtime**. Memo recommends; this design is
   runtime-agnostic.
5. **Schema versioning bump policy**. Today's `"1"`; when do we bump? Memo
   sets the rule (additive = no bump, removal/rename = bump).
