## Failure modes & how the prototype defends

| Failure mode | Defense | Tested by |
|---|---|---|
| Two parallel processes append to the same `run.log` and bytes interleave (the classic cross-process O_APPEND failure mode for writes > PIPE_BUF) | Per-source stream files — exactly one writer per file. Cross-stream merge happens at finalize time when all writers have closed (`cat` is safe). | `test-concurrent.sh` scenario B |
| Reader sees a half-written `manifest.json` mid-run | Atomic write via tmp+rename (`mv -f`) — POSIX guarantees atomicity. Reader either sees old content or new, never partial. | Implicitly: any read after finalize observes a complete manifest in `test-structure.sh` T6 |
| `latest` symlink stale (points to deleted run after retention) | Re-point on every finalize via `ln -sfn` (atomic on POSIX). Retention pass (Phase 1) re-points after deletion. | `test-structure.sh` T5 (re-point); retention not in T-0.4 scope |
| `command` field with shell metacharacters (`$`, backticks, etc.) corrupts manifest JSON | `json_escape()` via Python json.dumps (with sed fallback) before interpolation | `test-structure.sh` T6 ("command preserved == bun test"); regression-tested the original `source` bug |
| Run-id collision when two parallel runs start in the same wall second | Counter-suffix (`-1`, `-2`, …) loop in `start-run.sh` until a unique dir is found | `test-structure.sh` T7 |
| Bash `set -u` blowup on missing `.meta` keys | Defensive: `get_meta` returns empty string for missing keys; `[[ -f .meta ]]` guard before parse | Not directly tested; relies on start-run always writing all keys |

## Findings (3-5 bullets for the spike memo)

1. **Per-source streams + post-finalize merge is a clear win.** Zero
   corruption observed across 22,000 concurrent writes (2k shell-out +
   20k inline). The alternative — single shared `run.log` with `O_APPEND`
   — would have required per-write `flock(2)` and would fail on writes
   > PIPE_BUF (multi-line stack traces). Per-source files give us atomicity
   for free and make the merge order deterministic. **Memo recommendation:
   adopt per-source for Phase 1.**

2. **G2 (retrieval < 5s) is met with a ×95 margin.** A 7.2 MB run.log
   plus full manifest parse plus tail-200 lines completes in 48 ms
   median, 53 ms p99. Even on a cold disk and a 10× larger log, the
   budget is comfortable. **Memo conclusion: file-first storage is
   adequate for v1; SQLite (ARCHITECTURE §f v2) can wait until cross-run
   query patterns emerge.**

3. **The "p99 < 50ms" benchmark AC is ambiguous and needs Phase 1
   re-measurement.** Pure-bash on macOS cannot resolve sub-millisecond
   timings (no `EPOCHREALTIME`, python3 cold-start dominates). The
   amortized per-write number (17.2 µs) gives high confidence; per-syscall
   p99 should be re-measured in Bun/Node with `performance.now()` once
   the runtime decision lands in T-0.5. Document this carry-over.

4. **The original `source .meta` bug is a cheap lesson with broad
   applicability.** Sourcing a config file with values that contain
   spaces leads to silent word-splitting (`command=bun test` becomes
   `command=bun` then a separate `test` builtin call that fails under
   `set -e` — but only on parse, not at write time, so it's invisible
   in CI logs). **Memo / Phase 1 lesson: never `source` user-supplied
   config; always parse line-by-line with a known field-shape.** Captured
   in `finalize-run.sh` comments.

5. **Bash + python3 was the right pick for this iter.** Total ~590 LOC
   for prototype + tests, zero dependencies, single command to run.
   Phase 1 wrapping in TS/Bun stays equally cheap because all the heavy
   lifting (mkdir, append, cat, mv, ln) is filesystem-mediated, not
   in-process state. Re-implementing in TS would have been pure ceremony.

## Issues / pivots encountered

| Issue | Resolution | Cost |
|---|---|---|
| `source .meta` word-split `command=bun test` → silent failure under `set -e` | Switched to line-by-line `awk` parser + JSON-escape pass for values | ~5 min debug + ~10 LOC change |
| Per-write latency measurement using `python3 -c 'import time'` was dominated by python cold-start (~25ms each, ×2 = 50ms before measuring anything) → 359ms "p99" was nonsense | Pivoted to aggregate-throughput measurement (one timestamp at start of all 20k writes, one at end) → derived amortized 17.2 µs/write, throughput 58k writes/sec | ~10 min |
| `bash` brace expansion inside Python `[ ... ]` literal failed (`xs = sorted([10 20 30])` is a syntax error) | Pass timings as space-separated string, split inside Python | ~3 min |

No pivots required to the design itself — every T-0.3 §1-7 decision
held under implementation. The schema, layout, and concurrency strategy
are stable enough to lock for Phase 1.
